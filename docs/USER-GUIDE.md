# quilt-atlas — User Guide

For anyone (human or agent) who wants to know what the SuperInstance account *is* —
its scale, its families, which repos move, which have CI — and for researchers using
the studies and the SEED DNA catalog. No fleet background assumed.

## What you get

- **`atlas.json`** — the machine-readable map of the whole account, regenerated every 6
  hours by a scheduled GitHub Actions workflow: every repo with its family, the stage and
  keywords that classified it (`classification`), family membership, the 24 most recently
  pushed repos with their workflow files (`top_motion`), and pagination receipts
  (`pages_fetched`, `pagination_cap_hit`). At the 2026-10-04 run: 5,168 repos across 52
  pages, families `other=2717 · fleet=1591 · qthe=464 · quilt=299 · jev=54 · moth=25 ·
  latent=18`.
- **The README block** — the same truth rendered for humans between the
  `<!-- ATLAS:BEGIN -->` / `<!-- ATLAS:END -->` markers in the repo README, plus the
  top-motion + CI table.
- **`studies/`** — the account's research layer: pre-registered, receipt-backed studies
  (waves 71–78) with their data files under `studies/data/`.
- **`seed-dna/`** — the SEED DNA catalog: 47 study repos distilled to a language-free
  genetic code, with a machine-usable `seed-dna.json` (49 entries).
- **`NIGHT-SHIFT-REPORT.md`, `RELEASES-STATUS.md`** — two operational snapshots of the
  account (what shipped in the wave-67 night shift; the wave-66 publishing census).

Everything is free: the map is regenerated by GitHub Actions on the account's own free
tier, and reading it requires only `git` and optionally `jq`/`node`.

## Install

```bash
git clone https://github.com/SuperInstance/quilt-atlas
cd quilt-atlas
# Optional tooling for the examples below:
#   jq        — pretty-query atlas.json
#   node >=18 — only if you want to regenerate the map
#   gh CLI    — only as a convenient source of a token (gh auth token)
```

There is nothing to build. The repo is data + one zero-dependency script.

## First success in 5 minutes

```bash
# 1. When was this map made, and how big is the account?
jq -r '.generated_at_utc + " · " + (.total_repos|tostring) + " repos · " +
       (.pages_fetched|tostring) + " pages · cap_hit=" + (.pagination_cap_hit|tostring)' atlas.json
# Expected (as of this writing):
# 2026-10-04T12:20:07.272Z · 5168 repos · 52 pages · cap_hit=false

# 2. What are the families?
jq '.families' atlas.json
# Expected: {"other":2717,"fleet":1591,"qthe":464,"quilt":299,"jev":54,"moth":25,"latent":18}

# 3. Why is a specific repo in its family? Every assignment carries evidence:
jq -r '.classification["quilt-atlas"]' atlas.json
# Expected shape: ["quilt","name","quilt","JavaScript"]
#   → [family, stage, matched keywords, language]. Note the lesson baked into this
#   example: "quilt-atlas" is fleet-flavored, but the NAME stage checks family regexes
#   in precedence order (jev > latent > moth > qthe > quilt > fleet) and /quilt/ matches
#   first — so the repo is quilt, and the evidence tuple shows you exactly why.

# 4. Which repos moved most recently, and do they have CI?
jq -r '.top_motion[] | "\(.repo)  workflows=\(.workflows | join(","))  pushed=\(.pushed_at)"' atlas.json | head -5
```

If those four commands ran, you have read the account's ground truth — the same file the
scheduled bot regenerates.

## Everyday usage

### Know where a repo belongs (and audit the assignment)

```bash
jq -r '.classification["MicroMoth-quilt"]' atlas.json # → ["quilt","name","quilt","Python"]
# Surprised? The moth name regex is /moth/ (case-sensitive) and the repo name capitalizes
# "Moth", so the moth regex misses and quilt (later in precedence) matches instead. The
# README's moth prose lists MicroMoth-quilt as an example — the classifier's operative
# answer (in family_members.quilt, not .moth) differs, and the evidence tuple is the
# arbiter. Case-sensitivity of stage-1 matching is receipted here, not assumed.
jq -r '.classification | to_entries | map(select(.value[0] == "quilt")) | length' atlas.json
# → count of quilt-family repos (name + description stages combined)
```

The evidence tuple `[family, stage, matched keywords, language]` is the contract: never
trust the family, audit it. `stage` is one of `name`, `description`, `none`.

### List a family's members

```bash
jq -r '.family_members.jev[]' atlas.json        # all 54 jev repos
jq -r '.families_by_stage.name.fleet' atlas.json # how many fleet repos matched by NAME
```

### Check CI coverage on the moving frontier

```bash
jq -r '.top_motion[] | select(.workflows | length == 0) | .repo' atlas.json
# top-24 movers with NO workflows — honest gaps only for this slice; everyone else is UNMEASURED
```

### Regenerate the map (requires a GitHub token)

```bash
GITHUB_TOKEN="$(gh auth token)" node scripts/build_atlas.mjs
# Rewrites atlas.json + the README block; prints pagination + family summary to stdout.
git diff --stat   # see what changed since the last scheduled run
```

### Run a keyword-precision audit (the 54-c/55-c pattern)

```bash
ATLAS_DUMP=/tmp/atlas-dump.json GITHUB_TOKEN="$(gh auth token)" node scripts/build_atlas.mjs
# /tmp/atlas-dump.json = one row per repo: {name, description, family, stage, hits}
# Read the real description text beside the classification — audits read text, not vibes.
```

### Use the research layer

Read `studies/` top-down per program: the MECHANICAL-M1..M5 series is the
mechanical-learning program on the four-field cell (M1 books an honest registered FAIL —
P2 — that M2 then targets); REHYDRATION-72 derives the decay-curve scheduler; REFLEX-ROUTER-75
replicates the Jev reflex/reflect routing rule out-of-sample (28/28 at 38% of pure-reflective
cost). Each study header names its preregistration file and result JSON (usually copied
under `studies/data/`).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `Error: 401 https://api.github.com/...` on build | No/empty `GITHUB_TOKEN` | Export a token: `GITHUB_TOKEN="$(gh auth token)"` (any token that can read public repos) |
| `Error: 403 ...` mid-run | Rate limit (unauthenticated or exhausted) | Use an authenticated token; a fresh PAT gives 5,000 req/h — the run needs ~76 calls (52 page fetches + 24 CI probes) |
| A second generated block appears in README | You ran the builder from another directory so the ATLAS markers were not found | Run from the repo root; delete the stray block by hand (outside the markers) |
| Your hand-written text inside the markers vanished | The block is machine-owned | Write prose above `<!-- ATLAS:BEGIN -->` |
| `pagination_cap_hit: true` in atlas.json | The account exceeded 120 pages (12,000 repos) — the cap bounded the run | The count is bounded, not total; the receipt says so. Raise `PAGES_CAP` consciously |
| Family counts differ from what you quoted yesterday | The account moves between runs | Quote `generated_at_utc` with every number |
| `classification[repo]` is missing | Repo created after the last run | Re-run the builder, or wait for the next 6-hour cycle (cron `17 */6 * * *`) |

## FAQ

**Q: Why are 2,717 repos "other"? Is the classifier broken?**
No — it is honest residue by design. Families are assigned name-first, then by description
substring scoring against a small synonym table; anything matching neither stays "other"
rather than being guessed into a family. The README documents the audits (fleet 83% strict
precision, qthe 87%) that measured this imperfection instead of hiding it.

**Q: Can I see CI coverage for a repo that is not in the top-24 table?**
Not from the atlas. CI is probed only on the top-motion slice for API economy; absence
anywhere else is **UNMEASURED, never zero**. This is one of the map's three honesty laws
(with families-imperfect-on-purpose and receipted pagination).

**Q: What is the relationship between `atlas.json` families and the SEED DNA "families"?**
Orthogonal on purpose. Atlas families (jev/latent/moth/qthe/quilt/fleet) are *name-and-
description* clusters of the whole 5,168-repo account. SEED DNA families (substrates, time
organs, witness instruments, models-in-the-joint, swarm, organs, polyglot, creative skins)
are *functional* roles assigned by hand to the 47-repo study set. The SEED DNA catalog §1
states this explicitly.

**Q: Do the studies run from this repo?**
No. Studies are executed from the wave workspace harness (`scripts/`, `outputs/` of the
monorepo root); this repo holds the study documents and copied data artifacts
(`studies/data/`) as the citable record. The study headers cite both locations.

**Q: How current is the map when I clone?**
At most 6 hours + CI latency behind reality (cron `17 */6 * * *`, plus manual
`workflow_dispatch`). Check `generated_at_utc` and, if you need now-truth, re-run the
builder with your own token.

**Q: Is any of this authenticated beyond reading GitHub?**
No. Reading atlas.json/studies needs nothing. Regenerating needs a token that never leaves
your environment (in CI it is the workflow's own `secrets.GITHUB_TOKEN`). No other service,
key, or model is involved.
